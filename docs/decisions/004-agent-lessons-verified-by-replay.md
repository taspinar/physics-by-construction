# ADR 004: Agent lessons run behind a provider interface with a tool allowlist and are verified by replay

## Status

Accepted with the approval of the project bootstrap planning. The sandboxed
opt-in that "Alternatives considered" leaves to a new ADR is decided in
[ADR 010](010-coding-agent-exercises-on-the-learners-machine.md)
(2026-10-09), outside the harness; the decisions below are unchanged.

Date: 2026-10-06

## Context

The MVP must contain at least one lesson in which an LLM agent designs and
runs an experiment on a mechanics simulation, runnable locally with the
learner's own API key. Several requirements collide in that lesson:

- CI executes all lesson Python code, and a lesson whose code fails cannot be
  merged.
- LLM credentials are never stored in the repository or in CI for the MVP, and
  the site never calls an LLM.
- Code and results shown on the site are what CI ran and produced; anything
  not verified is marked.
- Lesson code isolates the provider behind a thin interface. The default
  provider is an unresolved question.
- Agent code that executes model-generated actions must state what the agent
  may do and must not grant arbitrary shell or network access by default.
  Keys must never be logged or printed.
- Builds are deterministic.

A live LLM call is non-deterministic, needs a credential, and costs money, so
CI cannot simply run the lesson.

## Decision

**Harness.** `src/pbc/agents/` provides a small experiment loop with three
parts:

1. A **model client interface**: given the conversation and the tool
   descriptions, return the next assistant message with zero or more tool
   calls. This is the only provider-facing surface.
2. A **tool allowlist**: an explicit registry of Python functions from
   `src/pbc` with typed, bounded arguments. Each lesson declares its allowlist
   and shows it on the page.
3. A **run loop** with a step limit that validates every requested call
   against the allowlist, executes it, and records a transcript.

**Capabilities.** The model's output is treated as data. The harness never
evaluates model-written code, runs shell commands, reads or writes arbitrary
files, or makes network requests on the model's behalf. The only network
traffic in a live run is the client's own request to the provider.

**Two client implementations.**

- A **live client** for one hosted provider, used only on the learner's
  machine. Its SDK is an optional dependency. The key is read from an
  environment variable and never printed, logged, or written to a transcript.
- A **replay client** that returns recorded model messages from a transcript
  committed next to the lesson. It needs no credential and no network.

**The committed transcript is a replay fixture.** It holds the recorded model
messages and, for each recorded tool call, the tool result of the recorded
run, which is the expected value for the comparison below. It holds no
credential and no provider request data. It is committed as a verification
input under the replay-fixture rule of ADR 002, at the declared fixture
location in the lesson directory; it is not a generated artifact in the sense
of that ADR.

**Verification by replay.** CI and the site build run the lesson with the
replay client. The recorded model messages are replayed, but every tool call
is executed again against the current simulation code. The replay fails if a
recomputed tool result differs from the recorded one beyond the lesson's
stated tolerance. The maintainer then re-records the transcript locally with
their own key.

**Presentation.** On the site, recorded model messages are labelled as
recorded output of a named model on a named date, not regenerated by CI. Tool
results and figures are the recomputed ones; the recorded tool results in the
fixture are never displayed.

**Provider choice.** The default hosted provider is not decided here. It is a
human decision taken when F09 is planned, as the requirements specify. Adding
or switching a provider means adding one client implementation.

## Alternatives considered

**Call a live LLM in CI with a repository secret.** Rejected: forbidden by the
requirements for the MVP, non-deterministic, costly, and it would expose a
secret to workflow changes.

**Do not execute agent lessons in CI; show a static, hand-pasted transcript.**
Rejected: the lesson's code would be unverified and could silently break, and
the page would show results no build produced.

**Record and replay raw HTTP exchanges with the provider.** Rejected: it ties
the recording to one provider's wire format, risks committing headers that
contain credentials, and does not re-check tool results against the code.

**Run a local open-weights model in CI.** Rejected for the MVP: large
downloads and slow inference against the CI budget, and still not
deterministic across hardware. It remains possible later as another client.

**Let the agent write and run Python.** A more capable agent, but it requires
a real sandbox and contradicts the requirement to withhold arbitrary
execution by default. Out of scope unless a later feature adds an explicit,
sandboxed opt-in through a new ADR.

## Consequences

Positive:

- Agent lessons are held to the same merge gate as every other lesson, with no
  credential anywhere in CI.
- The numbers an agent lesson shows are recomputed on every build, so a change
  to the simulation code cannot leave a stale transcript on the site.
- The provider is replaceable, and the unresolved provider question does not
  block the architecture.
- The security boundary is small and testable: the allowlist and its argument
  validation.

Negative, with mitigations:

- The model's reasoning shown on the site is a recording. It is labelled as
  such, which the content integrity requirement demands.
- A live run on the learner's machine will differ from the recording. The
  lesson says so and explains what should and should not be reproducible.
- Re-recording needs the maintainer's key and a manual step whenever
  simulation results change beyond tolerance. The replay failure message must
  say how to re-record.
- The live client cannot be exercised end to end in CI. Its request building
  and response parsing are unit-tested without network access; the first real
  call is verified manually by the maintainer when F09 is delivered.
