# ADR 002: Regenerate all lesson artifacts on every build and display code by reference

## Status

Accepted with the approval of the project bootstrap planning.

Date: 2026-10-06

## Context

The requirements state that the repository is the single source of truth, that
code shown on the site is the code CI ran, and that figures on the site are the
figures that code produced. They leave one choice to planning: generated
artifacts (figures, simulation outputs) are either regenerated by CI at build
time, or committed next to the code that produced them with a check that they
are up to date.

They also require content integrity: a claim on the site is backed by code or
proof that CI verified, and anything not verified is marked as such. That needs
a precise rule for how code, outputs, figures, and proofs may reach a page.

## Decision

**Generated artifacts are never committed.** Every build executes every lesson
and regenerates all figures, outputs, and rendered pages. Quarto's `freeze`
and any other committed execution cache are not used.

**Replay fixtures are verification inputs and may be committed.** An agent
lesson cannot regenerate a model's messages without a credential (ADR 004), so
its recording is committed as a replay fixture under these conditions:

1. It contains only the recorded model messages and the tool results expected
   for the recorded tool calls. It contains no credential, header, or other
   provider request data.
2. It lives at one declared fixture location inside the lesson directory. The
   path convention is fixed in F02, and the committed-artifact check exempts
   that location and nothing else.
3. Its recorded tool results are never displayed. Every build re-executes the
   tool calls and compares the recomputed results with the recorded ones
   within the lesson's stated tolerance; a mismatch fails the build. The page
   shows the recomputed results.
4. Its recorded model messages may be displayed only with the "recorded"
   label of ADR 004.

This is the requirements' second option, committed with a check that it is up
to date, applied to the one input a build cannot recompute. Figures, outputs,
and rendered pages stay regenerated without exception.

**Displayed material reaches a page only through verified display forms:**

1. Python code is either an executable cell that the build runs, or an excerpt
   included by reference at build time from the tested package `src/pbc/`.
2. Outputs and numbers are the output of executed cells, including values
   computed inline in prose.
3. Figures are produced by executed cells during the build.
4. Lean code is an excerpt included by reference from a file in the Lake
   project that `lake build` compiles.
5. Anything else must carry an explicit "not verified" marker that renders a
   visible label. A check fails the build for non-executed code without it.

By-reference excerpts are produced by small helpers in `src/pbc/authoring/`
that read the source of a named Python object or a named region of a Lean
file. No third-party include extension is required. The exact helper interface
is fixed in F02 (Python) and F08 (Lean).

**Reproducibility is defined at displayed precision.** Lessons show rounded
values, tests assert with explicit tolerances, and the CI runner is the
reference platform. Builds are byte-deterministic on one platform: seeds are
fixed, and figure output is configured to exclude timestamps and random
identifiers.

Reusable simulation code lives in `src/pbc/` with unit tests. Lesson pages
import it. Code that exists only to tell one lesson's story may live in that
lesson's cells.

## Alternatives considered

**Commit generated artifacts with a freshness check (including Quarto
`freeze`).** Builds would be faster and would not need the full Python stack.
Rejected because it creates a second copy of every result that can drift, puts
binary churn into Git history and pull request diffs, and needs a freshness
check that must re-run the code anyway to be trustworthy. Lesson simulations
are small enough to run on every build within the CI budget. Replay fixtures
are the narrow exception because their content cannot be regenerated in a
build, and their freshness check is the replay itself.

**Notebooks (`.ipynb`) with stored outputs as the lesson source.** Rejected for
the same drift problem, plus poor diffs and review.

**All code inline in lesson cells, no package.** Simplest display rule.
Rejected because lesson code must be unit-testable, importable by learners,
and callable as agent tools.

**A third-party include extension for code excerpts.** Rejected in favour of
project-owned helpers, to avoid an unpinned extension in the path of a core
integrity guarantee.

## Consequences

Positive:

- One source for every result. A page cannot show a stale figure or a snippet
  that differs from the tested code.
- Pull request diffs contain only human-authored changes.
- "Reproduce this" commands run the same files the build ran.

Negative, with mitigations:

- Every build pays the full execution cost. Budget: 30 seconds per lesson and
  3 minutes per site build (architecture, ADR 003). A lesson that needs a
  longer computation must reduce its problem size or mark a precomputed result
  "not verified".
- The site cannot be built without the Python toolchain. Accepted: the
  toolchain is pinned and installed by one tool.
- Cross-platform floating point differences mean a learner may see different
  digits beyond the displayed precision. Stated in the lesson template.
- Deterministic figures need explicit configuration and a check (F01, F02).
- The committed-artifact check must tell prohibited outputs from permitted
  replay fixtures. It does so by location only: the declared fixture location
  is exempt, and F09 registers its fixture there (F02, F09).
